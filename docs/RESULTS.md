**怎么读这组数字（口径纪律，勿简写）**：

- `hit@1=0.067` 与 `hit@10=0.746` 的巨大落差说明：**当前 FTS trigram 通道在"找得到"上很强，
  在"排在前面"上很弱**。这是 1.2.0 引擎挡位（向量/图谱）与实体链接的靶子，不是 bug。
- 按类目：**`cat3` h@10=0.438 最弱**——注意这是**推断/反事实题**
  （"Would Caroline pursue writing as a career?"），不是时序题，见下方勘误。
  类别定义以枚举实测为准，见下节。
- **本腿无向量挡位**，与金标腿（全通道）不可直接比较。

### 勘误（2026-10-03，1.2.0 卡二开工前发现）：类别语义之前写错了

原文把 `cat3` 标为「时序」并据此把 B-003 的 cat3 涨幅解释成「时序能力改善」。
**这是错的**——标签从未实证，是照着 LoCoMo 印象写的。把数据集里每类各打 6 道题
枚举后才定谳（值域枚举先于数值计算）：

| 类别 | 实际语义 | 题例 | n |
|---|---|---|---|
| cat1 | 单跳事实 | "What did Caroline research?" | 282 |
| cat2 | **时序 / 日期** | "When did Melanie paint a sunrise?" | 321 |
| cat3 | **推断 / 反事实** | "Would Caroline pursue writing as a career?" | 96（89 计分）|
| cat4 | 开放单跳推理 | "Why did Caroline choose the adoption agency?" | 841 |
| cat5 | 多跳推理 | "What does Melanie's necklace symbolize?" | 446 |

两处更正：
1. **真正的时序类是 cat2**，不是 cat3。1.2.0 卡三（时态/时序通道）的靶子应是 cat2。
2. B-003 里 **cat3 0.4382→0.7978 那笔账，我原写的因果解释作废**。
   它是推断题的涨幅，与时序无关。此前记的「cat3 时序面被向量道缓解」不成立，
   正确表述见 B-003 段（该段已按此更正）。

### 本轮实测到的两个坑（已修，防复发）

1. **K 位被候选截断**：首跑 `--top-k 1,3,5,10 --limit 50` 报 hit@10=0.4648，看似引擎弱；
   真相是 `limit` 只有 50，rank 50~99 的证据根本没被取回。改 `limit=100` 后 hit@10=0.7461。
   **教训：limit 必须 ≥ max(top-k)，否则测的不是引擎能力** → 已加 CLI 硬校验（非零退出）。
2. **引擎 limit 硬顶 100**：传 `--limit 120` 会让 1977 个案例**全部 degraded**、
   指标段全 `None`（诚实缺席设计生效，但白跑一轮）。已在 `mimir_v8/query.py` 抽出
   `MAX_QUERY_LIMIT` 常量供外部导入，`--top-k`/`--limit` 均在 CLI 层提前报错。

### B-003 · 1.2.0 卡一：接上向量道（同数据同参数的严格对拍）

**卡一做的不是新功能，是把「挡位」从散文变成一等对象**：
`report.engine` 里原来那句手写的 `"fts-only trigram + RRF (no vector lane)"`
与引擎行为无任何绑定——接上向量道后它仍会照写，且永不暴露。
现在改由 `QueryKernel.lane_profile(request).describe()` 自述，并配 CLI 硬校验：
`--vector` 给了却加载不上 → **非零退出**，绝不悄悄退回 fts-only 出数。

**可比性守卫（先证基线没被我改坏）**：同一份代码重跑 fts-only 腿，
逐 K 复现 B-002 的 `0.0668 / 0.0926 / 0.1290 / 0.7461 / 0.9464 / 0.9889 / 0.9975`、
mrr `0.18016`——**逐位一致**，故下列 delta 只能来自向量道本身。
数据集指纹同为 `79fa87e9…`；分母同样 1977/1977 计分、0 查询故障、9 条无证据剔除。

| K | B-002 fts-only | **B-003 vector+fts** | delta |
|---|---|---|---|
| 1 | 0.0668 | **0.5857** | **+0.5190** |
| 3 | 0.0926 | **0.7987** | **+0.7061** |
| 5 | 0.1290 | **0.8847** | **+0.7557** |
| 10 | 0.7461 | **0.9560** | +0.2099 |
| 20 | 0.9464 | 0.9889 | +0.0425 |
| 50 | 0.9889 | 0.9970 | +0.0081 |
| 100 | 0.9975 | 1.0000 | +0.0025 |

`mrr 0.1802 → 0.7137`。engine 段（引擎自述，非人手写）：
`vector+fts + RRF + anchor`，`active=["vector","fts"] disabled=["graph"]`。

**怎么读这组数字**：
- **改善集中在头部，不在尾部**：K=1~5 涨 0.52~0.76，K=20 之后几乎不动。
  这正对着 B-002 的结论——瓶颈是排序不是召回；向量道把召回到的东西**往前挪**，
  而召回覆盖本就接近饱和（0.9975→1.0000）。**这是排序机制该有的形状。**
- **cat3 涨幅须正确归因（2026-10-03 勘误）**：hit@10 `0.4382 → 0.7978`（n=89）。
  cat3 是**推断/反事实题**（"Would Caroline pursue writing?"），**不是时序题**——
  我原先写成「cat3 时序面被向量道缓解」，那个因果解释作废。
  这笔涨幅是**向量道连同 RRF 重排**在推断题上的合计效果，
  真正有时序语义的是 **cat2**（"When did Melanie paint a sunrise?"），
  要证时序能力得看 cat2 的消融腿（B-004）。
  其余类目 cat1 h@10 `0.9573` / cat2 `0.9094` / cat4 `0.9727` / cat5 更高。
- **不是金标腿的数字**：外部腿是一句一 session 灌进去的 reference fact，
  没有治理链、没有时态、没有图谱实体边。它证明的是**挡位开对了**，
  不等于「生产检索已达标」。

**本腿新踩的坑**：
3. **散文描述与引擎行为脱钩**（卡一病机本体）：上述硬编码字符串。已切引擎自述 +
   AST 级反向钉（禁止第二份会被执行的车道描述）。
4. **`--vector` 给不了时必须死**：静默退回 fts-only 会得到「engine 写着
   vector+fts、数字其实只经过 fts」的报告，比明着失败危险得多。已定专用异常
   `BenchmarkLaneUnavailable` → `exit(2)`，并断言 stdout 无任何指标段。
5. **短样本探的吞吐不能外推到长文本**：我用 11 字符短句测得 0.469 s/条，
   据此估全腿 ~1 小时；实际编码**长对话**远贵于此，全腿约 65 分钟（323% CPU）。
   估算数字必须标明它是在什么长度上测的。

## B-004 未跑：卡二「时序检索道」靶子证伪（2026-10-04）

卡二原计划加第四类车道（temporal），用 cat2（时序类）当靶。**开工前的值域枚举
把靶子证伪了，车道作废，B-004 不跑。** 详见 `docs/plans/1.2.0-card2-temporal-lane.md` §六。

### 三笔实测

**① loader 时间面成功（这一半交付了）**
`n_sessions=272  n_cases=1977  n_without_date=0  parse_rate=1.0000`
LoCoMo 全部 272 条会话日期解析成功。此前 `load_locomo` **从不读**
`session_N_date_time`，每条 session 的 `valid_from` 全空——时间数据根本进不了库。

**② cat2 的时间表达分族（枚举 320 条全文）**

| 族 | n | 占比 | 可寻址？ |
|---|---|---|---|
| P0 **无任何时间表达**（裸 `When did X …?`） | 275 | **85.9%** | 否——问题里没有时间信息 |
| P2 月+年 | 35 | 10.9% | 是 |
| P3 只有月无年（`in June`） | 5 | 1.6% | 否——缺年份，按「不猜」纪律弃用 |
| P4 只有年 | 3 | 0.9% | 是 |
| P1 日+月+年 | 2 | 0.6% | 是 |

**可寻址合计 40 / 320 = 12.5%**。全体 1977 题可寻址 255 条（12.90%）。

**③ 那 40 条现在排第几（B-003 向量道腿）**
可寻址 255 条 h@1=0.4588 / h@10=0.8745 / mrr=0.6076；
不可寻址 1722 条 h@1=0.6045 / h@10=0.9681 / mrr=0.7294。
**rank>10 的 32 条**（可寻址的 12.5%），其中 **7 条已 rank=1**。

### 为什么车道不做

1. **靶子面撑不起改动**：一条车道要改 `SIMILARITY_LANES`/`LANE_WIRING`/
   `QueryRequest`/RRF 权重/断路器/报告段共七处，换 cat2 上 40 条题的机会。
2. **头部已饱和**：40 条里 7 条 rank=1，最大缺口在 rank 11~30，而那批题的
   语义特征是「时间窗 + 人名 + 地点」，向量道已能抓到大部分。
3. **归因不纯（最硬）**：32 条 rank>10 混着两病——金标在**候选池外**（召回面）
   与金标**在池内排 50 名后**（排序面）。时序道只救后者。不分离，B-004 出了数
   也会把召回的功劳记到时序道头上。要分离得先跑 `--limit 500` 对照腿（未做）。

### 交付物

- **保留并交付**：loader 时间面（`SessionRecord.occurred_at`、
  `parse_locomo_date`、`n_sessions_without_date`、`report["temporal_data"]`）。
  独立价值：后续任何读时间的活儿（衰减/冲突消解/时间线）都从这一层起。
- **作废**：`SIMILARITY_LANES` 加 temporal、`QueryRequest.use_temporal`、
  `Kernel.temporal_candidates`、B-004 消融腿。相关 TDD 钉已随车道一并撤下。

### 可比性守卫：valid_from 写入不改既有排序（PARITY_OK，2026-10-04）

`occurred_at` 落进 `valid_from` 并非天然无害——`query.py` 的 `_decay_factor(...)`
与 `_not_yet_effective(valid_from)` **都读这一列**。对照腿（B-002 原参数：
`--top-k 1,3,5,10,20,50,100 --limit 100`，fts-only）结果：

- 15 项指标（hit/recall@1~100 + mrr）**逐位相同**；
- 五个类目 h@1/h@10/mrr **逐位相同**；
- **1965 个案例的 `first_rank` 一条未动**（最硬的一项：排序零挪动）。

**结论**：loader 时间面是纯数据面交付——写入 `valid_from` 后既有 fts 腿的
数字与 B-002 完全一致，`parse_rate=1.0` 的收益不付任何回归代价。

**对照腿 #1 作废记录**：首腿误用 `--limit 50` + top-k 少 100，
`hit@1` 因此假动（0.0668→0.0607）。候选池深度不同 = 进排名的 fact 集合
不同，根本不构成对拍；`hit_rate@100=None` 也是同一根因（K 列表不同）。
对拍脚本已改为**参数不一致即中止比较**（先对参数再对数字）。
另：`ps` 瞬时采样把满载进程读成 0.0% CPU，`top` 快照才见 100%——
判活看 `top`/`TIME+`，别信单次 `ps`。

### 本轮新增判例

**靶子要量「可寻址条数」，不是量「类目缺口」**：cat2 的 h@10 缺口 0.09 看着像
一块干净的靶地，实则 85.9% 的题**问题里根本没有时间表达**。类目缺口回答
「这批题答得差吗」，可寻址条数回答「这批题能被新机制改善吗」——**两问不同，
拿第一问的数字去立第二问的靶，会盖一条七处改动的车道在 12.5% 的题上**。
