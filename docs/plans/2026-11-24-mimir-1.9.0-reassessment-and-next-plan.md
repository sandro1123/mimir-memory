## 3. 本次新发现（修正我上一份审计）

### 3.1 Thor 的对话其实一直在被自动捕获
- `conversation_sources` 里有 `thor-bridge` 12 条（最新一条 11-24 07:43）、`odin-bridge` 1 条（11-23 17:38）。
- 这 24 条候选的结果：**committed 12、human_review 10、rejected 2**。
- 所以“Mímir 收不到 Thor 的对话”不成立。真正的问题在后面 4 个环节。

### 3.2 SessionStart 从来没有给 Thor 注入过底座
- 桥接进程每一轮都以 `resume` 方式启动，hook 遇到 resume 直接跳过（日志里每条 SessionStart 都是 `skip: source=resume`）。
- 结果：Thor **从来没有在开局拿到铁律、偏好这些底座内容**。这是用户感受到“它不记得”的主要原因之一。

### 3.3 身份是混的
- hook 里 `AGENT_ID=thor`，但用的 token 是 `~/.mimir_claudecode.token`，所以入库的 `owner_principal` 一律是 `claudecode`，只有 `connector_id` 能区分 Thor 和 Odin。
- 这意味着 1.9.0 给 `thor`、`odin` 加的别名**在当前链路上根本用不到**，因为没有任何请求是以 thor 或 odin 身份发出的。

### 3.4 候选质量差
- 有候选的 summary 就是原始对话，例如 `assistant: 先生，审计做完了…`，甚至 `user: <bridge_context>{"chatId"…`。桥接注入的系统上下文（bridge_context、bridge_instructions）**没有在结晶前剥掉**。
- 有的被判成“确定性噪声”拒掉，有的进了 human_review 继续积压。

### 3.5 fast_track 实际上就是自动入库
- Thor 候选中已有 12 条经 `fast_track 自动审批` 直接进了 facts。流程上走的是治理，符合 INV，但对用户来说效果就是自动入库。这个边界需要您明确认可。

### 3.6 查不到的原因（不变）
- `/v8/query` 只查 facts。10 条 human_review 的 Thor 候选、以及原始对话，在 `mimir` 搜索里都看不到。

### 3.7 治理服务假失败（不变）
- 去重闸拦截被当成失败返回 exit 1，24 小时内失败 66 次；同一条候选反复被重新处理。另有 systemd 配置改了但没有执行 `daemon-reload`。

## 4. 建议的开发计划（缩小范围、重新排期）

### 1.9.0「Honest Connect」：把已有链路修到可信，本周内完成

| 序 | 工作项 | 验收标准（可证伪） |
|---|---|---|
| 1 | **治理退出码**：`duplicate blocked` 视为正常结果；被拦截的候选写成终态（rejected/merged）并附原因，不再反复重试 | 治理服务连续 24 小时为绿；同一 candidate_id 不再重复出现 |
| 2 | **整理 diff**：统一换行符（`.gitattributes` 已有），把 CRLF 噪声与真实改动分开提交；**按事实重写 CHANGELOG** | `git diff -w` 等于真实改动；CHANGELOG 每条都能对上证据 |
| 3 | **SessionStart 支持 resume**：resume 时也注入底座，但做限流（例如同一会话 N 小时内只注入一次） | Thor 新会话第一轮能看到铁律和偏好；hook 日志出现 `injected` |
| 4 | **身份统一**：签发 thor、odin 独立 token（scope 为 read 和 ingest），hook 和 CLI 按调用方选 token；保留别名继承 | 新入库的 `owner_principal` 分别为 thor/odin；`mimir` 以本人身份查询 |
| 5 | **结晶前清洗**：剥离 bridge_context、bridge_instructions 和工具调用标记；summary 必须是提炼后的内容，不能是原文 | 新候选不再出现 `user: <bridge_context>` 这类原文 |
| 6 | **检索能看到待审内容**（需要您拍板）：`/v8/query` 增加可选的 `include_pending`，候选以 `pending` 标注、降权返回，**不写 facts** | 默认行为不变；加参数后能看到 Thor 的 human_review 候选，并明确标注“未审核” |
| 7 | **Odin 打通**：在 sanjose 上核查并挂载同一套 hook | `odin-bridge` 每天有新 source |
| 8 | **捕获断流告警**：thor-bridge 或 odin-bridge 超过 N 小时没有新 source 就推送提醒 | 故障注入（停掉 hook）后能收到告警 |
| 9 | **CLI 修整**：加 `--help`；结果显示 `recorded_at` 和来源；修掉无效的 `-t` | 查询结果能看出新旧和来源 |
| 10 | **热度与拍板对齐**：二选一，要么改成 shadow（只记录、不影响排序），要么正式翻案改成影响排序并写进 ADR | 代码行为和拍板记录一致 |
| 11 | **正式发布**：按 release 流程部署；`daemon-reload` 由您执行 | `/health` 返回 1.9.0；systemd 不再提示配置变更 |

## 5. 1.9.0 完成后，用户能得到什么（只写验收能证明的）

1. **Thor 和 Odin 的对话自动沉淀**：会话结束后自动摘要成候选，经治理进入长期记忆，不用手动 `remember`。
2. **开局自带底座**：Thor 和 Odin 每个新会话（包括 resume）第一轮就带着您的铁律和偏好。
3. **三端共享记忆，但身份分得清**：Thor、Odin、Claude Code 可以互查对方沉淀的内容，并且能看出每条记忆来自谁。
4. **能搜到“还没审完”的记忆**：加参数后，待审内容会以“未审核”标注出现，不会和已确认的事实混在一起。
5. **搜索结果可判断**：每条结果显示时间和来源；“没查到”和“通道坏了”会分开提示。
6. **后台安静且诚实**：治理服务不再假报错；捕获一旦断流，会主动提醒您。
7. **版本可信**：`/health`、CHANGELOG、实际行为三者一致。

**1.9.1 起**：Mirasim 托管的 agent 自动接入；Mímir 卡片定时发布到 Obsidian；审核积压可以批量处理。
**1.10 起**：能直接按实体或操作手册查询；LLM 断供时不丢数据，恢复后自动补齐。
