## B. 1.9.1 待办

### B1 今天发现的问题（优先）
1. **替换事实在生产上不可用（P1）**。生产 `facts` 表的 CHECK 只允许 `active/tombstoned/disputed/archived`，代码在替换时会写 `superseded/retracted`，所以 `POST /v8/facts` 只要带 `supersedes` 就会报 500 IntegrityError。
   - 修法：做一次 schema 迁移，SQLite 改约束需要重建表，迁移前必须先备份。
   - 迁移期间，API 遇到这种情况应返回明确的 4xx，不要返回 500。
   - 补一个用"生产旧 schema"跑的回归测试。
   - 今天的绕行：两条过时事实（`c92f0e94…`、`4f50fdee…`）用 PATCH 原地改到了 v3。
2. **venv 绑在旧 release 目录上**。`venvs/1.9.0-20261124_1139` 的 editable 安装指向已改名的 `releases/1.9.0-20261124_1136/`，现在全靠 `PYTHONPATH=releases/current` 才能加载。改法二选一：每个 release 建自己的 venv，或者改成非 editable 安装。部署脚本里加一条预检，确认 `import mimir_v8` 加载的是 current。
3. **部署时 worker 被连带杀掉**。governance 和 extract 依赖 `mimir.service`（`Requires=`），重启 API 时正在跑的 worker 会被 SIGTERM，算一次失败。部署手册要写明：重启前先停相关 timer，或者避开它们运行的时间；也可以考虑把 `Requires=` 改成 `Wants=`。
4. **临时提醒不可靠**。`systemd-run` 建的一次性提醒，机器重启就会丢。需要一个持久的一次性提醒机制。
