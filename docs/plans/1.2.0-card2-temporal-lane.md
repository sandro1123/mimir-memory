## 一、靶子是怎么定下来的（先量后写）

**类目语义以枚举实测为准**（我原先把 cat3 标成「时序」是错的，已在 RESULTS.md 立勘误）：

| cat | 实际语义 | n | B-003 vec@10 | 缺口 |
|---|---|---|---|---|
| 3 | 推断/反事实 | 89 | 0.7978 | 0.20 |
| **2** | **时序/日期** | **320** | **0.9094** | **0.09** |
| 1 | 单跳事实 | 281 | 0.9573 | 0.04 |
| 4 | 开放单跳 | 841 | 0.9727 | 0.03 |
| 5 | 多跳推理 | 446 | 0.9888 | 0.01 |

**选 cat2（时序）而非 cat3（缺口更大）**，理由：cat3 只有 89 个样本，拿它定一条通道的
成败，噪声大于信号；cat2 有 320 样本，且它是**唯一一类答案本身带明确时间语义**的题。

## 二、病机（已实证，不是推测）

**两处，二者缺一则时序通道拿不到任何可用的东西**：

1. **LoCoMo loader 把会话时间戳扔了**。`benchmarks_external.py:95-107` 只从 turns
   拼 `speaker: text`，**从未读过** `session_N_date_time` 字段（我 1.1.0 首跑时核过：
   288 个 `_date_time` 是日期字符串，不是会话正文）。后果：每条 session 进库时
   `valid_from`/`valid_to` 全空，时序面**没有任何数据可读**。
2. **Chronos 是「衰减」不是「时序检索」**。`query.py:911` `_decay_factor` 按
   `valid_to` 是否过期 + `decay_tier` 半衰期算权重，相对的是 **`updated_at`**。
   对基准语料而言 `updated_at` = 入库时刻 → 一段 2023 年的对话被当成刚写的。
   **衰减机制不能回答「当时发生了什么」**，这是两件事。

**结论**：卡二不是给引擎加一个开关，是**先把时间信息送进系统**，再让检索读它。

## 三、契约

### 3.1 loader 侧：`SessionRecord` 加时间面

```python
@dataclass
class SessionRecord:
    session_key: str
    owner: str
    text: str
    occurred_at: str | None = None   # ISO-8601，会话发生时间（新增）
```

`load_locomo` 解析 `session_N_date_time` 的对应值写入 `occurred_at`。
**解析失败必须显式计数并留痕，不得静默吞掉**（沿用既有
`n_skipped_no_evidence` 口径，新增 `n_sessions_without_date`）。

### 3.2 写入侧：benchmark 写入时把 `occurred_at` 落进 `valid_from`

`_ingest_sessions` 的 `CreateFact(..., valid_from=record.occurred_at)`。
`valid_from` 已有列、已有写入路径（`store.py:992`），**零迁移**。

### 3.3 检索侧：temporal lane（第四类车道）

- `SIMILARITY_LANES` 加 `"temporal"`；`LANE_WIRING["temporal"] = ("temporal",)`。
- `QueryRequest.use_temporal: bool = True`。
- 通道语义：**问题里出现时间锚点时**，把「问题时间锚点 ∈ 候选 fact 的
  `[valid_from, valid_to]` 窗口」作为一路 RRF 信号。
  时间锚点靠 `QueryKernel` 的 `TEMPORAL_HINTS`（`when/when did/on what date/
  哪年/什么时候/多久前/几月`）**先做便宜的模式判定**——不是 NER，起步可测。
- **不引入日期解析依赖**：无法解析的时间表达**不进这条道**（计数留痕），
  绝不猜一个日期去参与排序。

## 四、TDD 三钉

**正向**
1. 一条 `valid_from=2023-05` 的 fact + 含「when」的查询 → temporal 进 `active`，
   候选池含它，`describe()` 含 temporal。
2. 时间锚点落在 `[valid_from, valid_to]` 内的 fact，其 RRF 贡献 > 落在窗口外的。
3. loader 对真实 LoCoMo 解析出 `occurred_at` 的 session 数 > 0 且
   `n_sessions_without_date` 与之相加 = 总 session 数（三者恒等）。

**边界**
4. `occurred_at` 解析失败（脏日期串）→ 该 session 计入 `n_sessions_without_date`
   且照常入库，**不得整批丢弃**。
5. 无时间锚点的查询 → temporal 道 `active` 但**零贡献**（不得无端扰动排序）。
6. `valid_from` 缺失的 fact → 窗口判定为「不匹配」而非「全匹配」
   （缺数据不等于处处适用）。

**反向（本卡核心守卫）**
7. **解析不了的时间表达不得被猜成日期**：给 `next tuesday`，断言它既不进 temporal
   信号也不抛异常，且计数 +1。
8. 注入一条 `valid_from` 在未来的 fact + 过去时间锚点的查询 → **不得**被 temporal
   判为命中（`_not_yet_effective` 的语义不得被绕过）。
9. 关掉 `use_temporal` → temporal 进 `disabled` 且指标可复现 B-003
   （回归守：不许让新道偷偷改变既有腿的数字）。

## 五、验收判据

**B-004 = 同数据同参数的 cat2 消融腿**：带 temporal 道 vs 不带，两腿都要跑。
- 首要判据：**cat2 hit@10 相对 B-003 的 0.9094 有提升**，且整体 hit@10 不回退。
- **必须同时报三件事**（缺一件即视为口径作弊）：
  ① cat2 前后对比 ② 全类目对比 ③ temporal 道的实际贡献条数
  （若贡献为 0 而数字却涨了 = 别的东西在动，定谳前不许归因给本卡）。
- `n_sessions_without_date` 要写进报告——**解析率本身就是结论的一部分**。

## 六、定谳（2026-10-04）：靶子不成立，车道作废

写 SPEC 时我拿 B-003 的类目数字选了 cat2（缺口 0.09、n=320），**但没量
「这些题里到底有几条带时间表达」**。施工前的值域枚举把这个洞翻出来了。

### 6.1 三笔实测

**① 时间面数据到位了**（loader 侧成功）
`n_sessions=272  n_cases=1977  n_without_date=0  parse_rate=1.0000`
LoCoMo 全部 272 条会话日期**全部解析成功**，`fromisoformat` 解析不了这件事
是真的，但写完解析器后一条不漏。§三.1/§三.2 达成。

**② cat2 的时间表达分族（枚举 320 条全文后归类）**

| 族 | n | 占比 | 可寻址？ |
|---|---|---|---|
| P0 **无任何时间表达**（裸 `When did X …?`） | 275 | **85.9%** | ❌ 问题里没有时间信息 |
| P2 月+年（`in March 2023`） | 35 | 10.9% | ✅ |
| P3 只有月不有年（`in June`） | 5 | 1.6% | ❌ 缺年份，按「不猜」纪律弃用 |
| P4 只有年（`in 2010`） | 3 | 0.9% | ✅ |
| P1 日+月+年 | 2 | 0.6% | ✅ |

**可寻址合计 40 / 320 = 12.5%**。全体 1977 题里可寻址 255 条（12.90%）。

**③ 那 40 条现在排第几（B-003 向量道实测）**
可寻址 255 条：h@1=0.4588 h@10=0.8745 mrr=0.6076；不可寻址 1722 条：
h@1=0.6045 h@10=0.9681 mrr=0.7294。
**rank>10 的共 32 条**（占可寻址 12.5%）。

### 6.2 为什么车道仍然不做

1. **靶子面太小**：一条车道要改 `SIMILARITY_LANES`、`LANE_WIRING`、
   `QueryRequest`、RRF 权重、断路器、报告段——七处改动面，
   换来 cat2 上 40 条题的机会。按「先量后写」，40 条（12.5%）撑不起。
2. **头部已饱和**：40 条里 **7 条已经 rank=1**，最大的一批缺口在
   rank 11~30（Calvin/Andrew/Dave 那批），而那些题的语义特征是
   **「在 2023 年 X 月」这个时间窗 + 人名 + 地点**，向量道已经能抓到大部分。
3. **归因不纯（最硬的一条）**：那 32 条 rank>10 里混着两种病——
   * 金标在候选池外（召回面问题：limit=50 截断或压根没召回）
   * 金标在池内但排 50 名之后（排序问题：候选池深度）
   时序道救的是第二种。**不分离这两者，B-004 出了数也归因不到本卡头上**
   ——拿召回的功劳记在时序道，正是判例 #144「算错了先别写」的同族。
   要分离，得先跑 limit=500 的对照腿（未做）。

### 6.3 保留什么

**保留 §三.1/§三.2（loader 时间面）**，理由与车道无关：
时间数据此前**根本进不了库**（`valid_from` 全空）。现在 `occurred_at`
解析率 1.0、写进 `valid_from`、报告带 `temporal_data.parse_rate`。
这条通道独立有价值——**后续任何要读时间的活儿（衰减、冲突消解、
时间线视图）都从这一层起**，不必再回头补数据。

**作废 §三.3（temporal 车道）与 B-004 消融腿。**
`tests/test_temporal_lane.py` 的 9 钉不删——其中 2 钉（loader 侧）
已 GREEN，是 loader 的回归守；7 钉（kernel 侧）转为**待启用**，
等真出现「问题里带时间表达」的题族时再开。

时间面**不进** 1.2.0 车道清单，作为 loader 层基建挂账。
