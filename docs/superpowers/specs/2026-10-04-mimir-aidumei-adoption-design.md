# Mímir 吸纳 aiduMEI 设计文档 · 「可信底座 × 认知闭环」双轨路线

- 日期：2026-10-04
- 状态：待用户审阅（brainstorming 架构路径 → spec → plan）
- 对标基线：aiduMEI f0.3+（10-03）vs Mímir 1.1.0（schema 21）+ 1.2.0 在途
- 决策链：B（护城河+认知层）→ B2（RECALL 漏斗+PULSE 先行）→ C1→C2→C3（双时间轴→自编辑→Reflect）→ D2（轻量化放 1.4.0）

## 一、总纲（一句话）

Mímir 不做 aiduMEI 的复刻，做「**用 Mímir 的治理基因重做 aiduMEI 的认知能力**」——每件搬进来的能力都要过 Mímir 的三道门（候选→审批→入库 / 事件溯源 / 诚实判语）。这是和 aiduMEI 的本质区别，也是护城河不被稀释的保证。

## 二、为什么是 B 路线（决策依据）

Mímir 的护城河（治理管线 / 事件溯源账本+谱系链 / 联邦 CRDT+Grants / 诚实遥测）是 aiduMEI 架构基因里没有的——aiduMEI 的 consolidator 是"后台清理"，Mímir 是"入库前审批"；Pantheon 是"多 Agent 共用一套库"，Mímir 是分布式协议级联邦。为追功能数量稀释这条轴是亏本买卖。

但"认知闭环"（反思+自编辑+双时间轴）恰是 Mímir 已有事件溯源账本的**自然延伸**：账本里有全量"谁记的、改过几版、谁批准的"，Reflect 只是定期读账本提炼洞察；dedup 已有 Jaccard top-K，升级成 LLM 语义判重是顺水；1.2.0 卡二 loader 已把 `occurred_at` 做出来（parse_rate=1.0），补双轴是顺手。三件全是"地基已有一半"的嫁接，成本最低、收益最大，且不动联邦/治理根本。

人格基座 / 多模态 / 41 个 MCP 工具不碰：前两者与"联邦底座"定位不匹配（人格是单 Agent 概念，多模态是存储形态扩张），后者是生态量不是架构件。

## 三、1.3.0「看得见 + 变聪明」（主题版，五件）

### ③-1 RECALL 召回漏斗 trace（P0，灵魂件）

**做什么**：一次检索的全链路可观测——候选池 → 三路召回（FTS/向量/graph，各自命中数+耗时）→ 去重（dedup 命中数）→ 时间衰减（衰减掉多少）→ RRF 融合 → 最终 N 条。每步耗时与命中数全可见，每步带 verdict。

**嫁接点**：`mimir_v8/query.py` 已有 `recall_verdict ∈ {found, not_found, degraded}` + `_evidence_for` 证据召回 + 三路检索断路器状态。漏斗是把这些已存在但"只在日志里"的信号结构化成 trace 对象。

**与 aiduMEI 的区别（必须更诚实）**：aiduMEI 漏斗展示"每步耗时与命中数"；Mímir 漏斗每步还要带 verdict——"没查到"和"通道坏了"永不混淆。degraded 通道的步要显式标红而不是静默吞掉（P0-E 断路器的教训：故障先于缺失）。

**数据结构**：新增 `RecallTrace`（dataclass）：stages 列表，每 stage = {name, verdict, hits, elapsed_ms, detail}。`POST /v8/query` 加 `?trace=true` 参数返回 trace；默认不返（性能）。

**验收**：trace 开关下一次检索返回全阶段（候选池→三路召回→去重→衰减→融合/最终，每步全量）；任一通道 mock 故障时对应步 verdict=degraded 且最终 verdict=degraded（不停在 found 上撒谎）；耗时字段全非空。

### ③-2 控制台升级（P0，与漏斗同批）

**做什么**：两块——（a）PULSE 健康面板升级（版本/代号/核心模块探针/四层存量+容量水位）；（b）RECALL 漏斗面板（③-1 的可视化）。MAP 星图 / SETTINGS 只读配置 / VAULT 检索面板**本次不做**（B2 决策）。

**嫁接点**：现有 dashboard（FastAPI backend + 独立 frontend）。本次不强求"后端托管 /ui 纯静态"（那是 aiduMEI 的形态，Mímir 的 dashboard 已有独立部署链，硬改部署形态风险大于收益）；只做面板级升级。是否迁移到后端托管，留 1.4.0 与轻量化一起议。

**验收**：PULSE 面板 11 个核心模块探针全绿可点；RECALL 面板输入 query 即出漏斗五步；与现有 VAULT 检索面板数据一致（同一 query 两处结果逐位对上）。

### ③-3 双时间轴 valid_from/valid_to（P1，C1 先行）

**做什么**：每条 fact 补 `valid_from / valid_to`（NULL=永久有效，铁律类永不过期）；检索时过期事实降权不删除，未生效事实排后；`recorded_at → valid_from` 三级时间源回退（created_at → recorded_at → valid_from，取最可信）。

**嫁接点**：1.2.0 卡二 loader 已产出 `occurred_at`（parse_rate=272/272=1.0，时间数据已能入库）。本件是把 loader 的产出接入检索：schema 加两列（守卫式迁移，参考 1.1.0 schema 20→21 的 MIGRATABLE_* 模式）+ 检索融合加时间衰减项（λ 环境变量可调，抄 aiduMEI 的单真相源做法）。

**卡二教训的应用**：卡二时序道被证伪（cat2 320 条只有 12.5% 带可寻址时间表达）——所以本件开工前先量生产库 686 条 facts 里有多少带 occurred_at，有靶子才做衰减项；没靶子就只做双轴存储+展示，不做检索加权（宁缺勿脏）。

**验收**：双轴列守卫式迁移零丢数；过期事实检索降权可演示（同一 query，过期/未过期排序差可复现）；铁律类永不过期有测试钉死。

### ③-4 自编辑去重 LLM 判重（P1，C2 其次）

**做什么**：写入新记忆前，LLM 判断与既有记忆的关系：重复→合并（不追加）、冲突→保留双方并标注置信度+时间、全新→入库。每次合并/冲突更新把「旧内容→新内容」快照进编辑历史表，一键回滚。

**嫁接点**：现有 `dedup.py`（Jaccard top-K 召回）做第一层零成本兜底；LLM 判重做第二层语义判定；LLM 不可用时无缝回退纯 Jaccard（向后兼容）。判定走治理管线（candidate→审批），LLM 只能建议不能 commit（抄 aiduMEI 自己的铁律，也是 Mímir 基因）。

**验收**：重复写入合并（库增长 0）；冲突写入保留双方+置信度标注；回滚恢复旧内容逐位对上；LLM 不可用时退化到 Jaccard 且测试覆盖该路径。

### ③-5 Reflect 主动反思（P1，C3 最后）

**做什么**：后台定期（默认 6h 可调）+ 会话结束触发，回顾账本提炼模式/矛盾/知识缺口，落库成一等公民 `reflections`，供后续检索注入引用。同一洞察按 content 哈希幂等；LLM 失败时返回空洞察不抛异常。

**嫁接点**：事件溯源账本（谁记的、改过几版）是反思的最佳输入——比 aiduMEI 的"读 facts 表"更富。产出走治理管线入库（候选→审批）。依赖 ③-3（反思需要知道"什么时候的事"）和 ③-4（反思产出不和存量打架），所以放最后。

**验收**：定时+手动双触发可演示；洞察落库后可被检索命中；重复触发幂等（content 哈希去重）；LLM 失败路径有测试。

## 四、1.4.0「跑得轻 + 收得拢」（跟随版，两件）

### ④-1 轻量化 lean 挡位

给"不要 Chroma 重部署"的用户一条 lean 路径：FTS-only 挡位（基准 runner 里 engine 如实标注已有雏形）/ 可选嵌入式向量库。接 `Dockerfile.lean` 雏形。与 1.3.0 正交，单独立版。

### ④-2 递归精炼（多对一聚类压缩）

后台把相关多条碎记忆递归合并为高层抽象，对抗记忆熵增。与自编辑分工：自编辑管写入时 1 对 1，精炼管后台多对 1。产物 soft-superseded（不物理删除）+ 一键回滚 + LLM 只建议不 commit。与 retention 衰减互补。

## 五、三条硬纪律（吸纳过程的护栏，不可议价）

1. **治理基因不稀释**：每件新能力产出的记忆（反思洞察、合并结果、精炼产物）一律走候选→审批→入库，LLM 只能建议不能 commit。
2. **诚实判语不打折**：漏斗每一步都要有 verdict；verify 三态、recall 三态的语义在本轮任何新代码里不得弱化（degraded≠empty 的 P0-E 教训）。
3. **先量后写**：每个 1.3.0 件开工前，先量生产库里有多少真靶子（1.2.0 卡二 12.5% 的教训：靶子要量"可寻址条数"不是量"类目缺口"）。没靶子不开工，开工先写 RED 测试。

## 六、非目标（明确不做，防蔓延）

- 人格基座（Persona Memory Layer）：单 Agent 概念，与联邦底座定位不匹配。
- 多模态视觉记忆 / Obsidian 双链：存储形态扩张，不在本轮。
- 41 个 MCP 工具生态对标：生态量，Mímir 的 MCP 按需加（27 工具 skill 路由已有）。
- MMR 多样性 / echo 抑制：检索微调，RRF 够用时不做。
- 控制台后端托管 /ui 纯静态化：部署形态变更，留 1.4.0 与轻量化一起议。

## 七、里程碑与依赖图

```
③-3 双时间轴 ──┐
               ├→ ③-5 Reflect（吃两者红利，最后）
③-4 自编辑 ────┘
```

## 八、风险与回退

- ③-3 schema 迁移：走 1.1.0 守卫式迁移模式（MIGRATABLE_* + 提版必配迁移段），生产先快照（.backup 零接触三表守卫式）。
- ③-4 动写入路径：LLM 判重默认 dry-run 一段观察期（抄 aiduMEI consolidator 三级的 dry-run 默认），确认无误伤再 apply。
- ③-5 后台任务：走现有 timer  cadre（15 单元 drop-in 模式），失败不阻塞主链（fail-safe 主链不吞的判例）。
- 任一件验收不过：独立回退，不拖累其他件（件间无运行时依赖，只有 ③-5 对 ③-3/③-4 的数据依赖）。
