> **状态**：Design Spec（待人工批准）
> **目标版本**：v1.7.0（路线图原定 "The Obsidian Bridge"，本次据实扩写为双向反哺）

## 1. 意图与缘起

### 1.1 用户原话（意图来源）

> "obsidian笔记库未来就是记忆系统以外的知识系统中枢之中最关键的节点，
> 知识系统可能要围绕obsidian去塑造，知识系统与记忆系统相互形成反哺。"

> "混居吧，做好重新整理，把现有的文档能整合优化的内容也整合一下。"

> "有一些内容可能不要紧记忆系统，但他知道有这么个文件，必要时候可以来看。"

### 1.2 为什么现在做

2.0 设计稿把 Obsidian 定位为"人类阅读端口"，是**单向投影**。本次实地勘察后，
真实需求比这更大：库要成为**知识中枢本身**，与 Mímir 记忆系统**互相反哺**。
这不是推翻 2.0，而是把 2.0 §6 的"单向发布"升级为闭环。

### 1.3 实地勘察发现（实测）

> **权威数据来源**：`docs/vault-inventory/2026-10-29.json`
> （由 `scripts/vault_inventory.py` 生成，可复跑）。
> 下表为 2026-10-29 复跑结果；2026-10-28 的手扫初值是 638 篇/52 死链/227 链接，
> 差异因库在持续变化（Syncthing 同步中），**以制品为准**。

| 事实 | 实测（2026-10-29） |
|---|---|
| 库内 md 总数 | **640** |
| 角色分布 | unknown 321 / machine-log 184 / worklog 80 / versioned 20 / raw 15 / hub 12 / reference-only 8 |
| 全库链接总数 | **144**，其中**死链 54** |
| 孤岛（无出入链） | **534 篇** |
| git 覆盖 | **仅 120 篇被跟踪，518 篇（81%）从未提交** |
| 三大桶占比 | QuantStar 207 / Mímir 159 / 旧沉积 93 = **72%** |
| 目录形态 | PARA + 编号（`10-项目`/`20-领域`/`30-知识库`/`60-敏感信息`…） |
| 已存在的索引层 | `首页.md` 是精心写的导航 hub（全库仅 12 个 hub） |
| 索引层状态 | **已腐烂**——hub 指向 `90-自动同步/Mímir 事实/`，实际目录已改名 `90-自动同步_已归档_v3/` |

**核心诊断**：用户看到的"星状分布图、乱得不行"不是"没结构"，而是
**索引层腐烂**：hub 存在，但辐射出去的线大半是断的（改名不同步、死链无人修），
且 **534 篇孤岛**从未被挂到 hub 上。库只被"摄入"（`VaultCollector` 全量读），
从未被"回流"（无任何 Mímir→vault 的写入路径，除日报外）。

**阶段 1 追加发现（凭据外溢）**：`reference-only` 原本只按目录判定，
实测发现 **3 篇非敏感目录的笔记里躺着真实 `sk-` 密钥**
（`10-项目/LangBot 飞书机器人.md`、`70-日记/2026-06-11.md`、
`90-自动同步_已归档_v3/Mímir 事实/0a4c958facdc75c7.md`）。
这些笔记若按原逻辑会判成知识节点并被结晶、投影到 Syncthing 同步的库中。
已加入凭据形态检测（只降级、不升级），见 `CREDENTIAL_PATTERNS`。


### 1.4 已存在但未通电的机制（关键复用点）

| 机制 | 位置 | 状态 |

**结论**：1.7.0 的一半工作量是**给已造好的保护机制通电**，不是从零发明。

## 2. 目标、非目标、反目标

### 2.1 目标

1. **回流闭环**：Mímir 把实体结晶为带双链的卡片写入库，形成 Mímir→vault 通路。
2. **索引层重建**：为库建立并维护索引层，修复死链，把孤岛挂到 hub 上。
3. **文档角色分型**：摄入时给每篇标注"角色"，不同角色走不同策略（见 §3）。
4. **仅索引角色**：允许声明"Mímir 知道此文件存在、可列出，但不读内容、不结晶"。
5. **安全网先行**：任何写入/整理前，先把 518 篇未跟踪文件纳入 git 快照。
6. **上下文不爆炸**：所有对 agent 暴露的接口必须带预算与降级（见 §6）。

### 2.2 非目标

1. 不自研富文本编辑器（阅读编辑 100% 靠 Obsidian 原生）。
2. 不做全网爬虫（信源仍由 `sources.yaml` 管控）。
3. 不重写用户的**过程稿正文**（见反目标 2）。
4. 不追求双向实时同步（避免死锁脏读，见 §4.3）。

### 2.3 反目标（坚决不做）

1. **严禁在安全网建成前动库**——518 篇未跟踪，改坏无法用 git 救回。
2. **严禁改写过程稿正文**——用户明确："2 是沉淀的过程稿，也有价值"。
   过程稿只做**归档/索引/标注**，正文一字不动。
3. **严禁静默覆盖任何非托管区块**——复用 `replace_managed_sections`
   与 `human_content_hash`：机器只写 `<!-- mimir:managed -->` 标记内的内容，
   标记外的一切字节不变；每次写入前校验 human_content_hash 未变。
4. **严禁把敏感目录内容摄入记忆系统**——`60-敏感信息/` 走"仅索引"。
5. **严禁虚报成功**——恪守 1.4.0 预算诚实协议。

## 3. 文档角色类型学（开放表，非封闭枚举）

**关键设计**：角色**不是硬编码枚举**，而是**声明式角色表**（类比 `sources.yaml`），
可扩展。未声明的类型走**最保守策略**（仅索引，不结晶）。

| 角色 | 判定依据 | 图谱角色 | Mímir 策略 |
|---|---|---|---|
| `hub` 骨架-索引 | 文件名含"索引/首页/README/index" 或显式声明 | 连接者 | 巡检维护、修死链、补孤岛 |
| `topic` 主题-正文 | 显式声明，或落在 `20-领域`/`30-知识库` | 知识节点 | 结晶成实体、回流双链 |
| `versioned` 过程稿-版本快照 | 文件名含版本号 + 白皮书/手册类 | 历史层 | 标注现行版；旧版留档不投影 |
| `worklog` 过程稿-工作记录 | 显式声明，或落在 `分层讨论`/`逐层审计`/`审计` | 时间线 | **正文不动**，仅归档 + 索引 |
| `machine-log` 机器日志 | `type: mimir-daily-report` 等机器 frontmatter | 沉积物 | 折叠成时间线索引页 |
| `reference-only` 仅索引 | **显式声明**（默认仅 `60-敏感信息/`） | 不参与 | 登记存在、可列出，**不读内容、不结晶** |
| `raw` 素材-原始 | 落在 `素材池/` 等 | 待加工 | 暂不处理 |
| `unknown` 未分类 | 兜底 | — | **仅索引**（最保守） |

**用户确认**：目前"仅索引"只有 `60-敏感信息/`，未来可能增加 →
故做成**可配置清单**，不改代码即可扩展。

## 4. 架构

### 4.1 双向反哺回路

```
        ┌────────────────────────────────────────────────┐
        │            Obsidian Vault (知识中枢)            │
        │  hub 索引层 · topic 正文 · 过程稿 · 机器日志    │
        └───────┬────────────────────────────┬───────────┘
                │ ①摄入 (已通电)              │ ②回流 (新增)
                │ VaultCollector             │ ObsidianPublisher
                ▼                            ▼
        ┌────────────────────────────────────────────────┐
        │                Mímir 记忆系统                   │
        │  entities · fact_entities · 事件溯源哈希链      │
        │  PublicationService (managed sections 保护)     │
        └────────────────────────────────────────────────┘
```

- **①库→Mímir**：`VaultCollector` 已有。**本次增强**：摄入时按 §3 打角色标签。
- **②Mímir→库**：**本次新增**。经 `PublicationService` 发布，走 managed sections。
- **③索引巡检**：**本次新增**。`VaultIndexer` 扫描全库链接图，修死链、找孤岛。

### 4.2 组件

| 组件 | 职责 | 复用/新建 |
|---|---|---|
| `VaultRoleResolver` | 按 §3 角色表给文档定角色 | 新建（读声明式角色表） |
| `ObsidianPublisher` | 实体→卡片 Markdown 写入库 | 新建，调 `PublicationService` |
| `VaultIndexer` | 链接图分析、死链检测、孤岛发现 | 新建（纯读，先只报告） |
| `GitProtector` | 写入前自动 git 快照 | **新建**（2.0 稿要求但从未实现） |
| `PublicationService` | managed sections 保护 | **复用（通电）** |
| `VaultCollector` | 摄入 | 复用，增角色标注 |

### 4.3 为什么不是双向实时同步

2.0 §6.0 已裁决：避免双向回写死锁。本次沿用——Mímir **只写自己的托管区块**
与**自己命名空间下的卡片**；用户在 Obsidian 里的编辑，靠**下一轮摄入**感知，
不做文件系统级监听。

## 5. 分阶段交付（每阶段可独立验收）

> 次序不可颠倒：安全网→清册→回流→巡检。

### 阶段 0：安全网（前置，必须先做）
- **产出**：518 篇未跟踪文件纳入 git；`GitProtector` 落地。
- **验收**：`git status` 干净；对任一文件做改动 → 可从快照一键还原。
- **风险**：无（只增不改）。

### 阶段 1：清册与角色分型（只读，不改库）
- **产出**：638 篇的**角色清册**（角色 + 理由 + 计划动作），产出报告供人审。
- **验收**：清册覆盖 100%；用户能逐类核对"这个判断对不对"。
- **风险**：无（纯读）。

### 阶段 2：回流闭环（写 Mímir 自己的卡片）
- **产出**：`ObsidianPublisher` 通电；`PublicationService` 接入；
  实体结晶为卡片写入**新命名空间**（不碰既有文件）。
- **验收**：写入一篇卡片 → 非托管区块零改动（用 `human_content_hash` 证明）；
  重复写入幂等；写入前有 git 快照。
- **风险**：中——首次写库，但只写新文件。

### 阶段 3：索引层重建（开始动既有文件）
- **产出**：修 52 条死链；为 96 篇日报 + 100 篇审计建时间线索引页；
  573 篇孤岛挂到 hub。
- **验收**：死链归零；star 图出现结构。
- **风险**：高——动既有文件。**前置**：阶段 0 的安全网 + 阶段 1 的清册经用户批准。

### 阶段 4：角色专属策略（版本快照折叠等）
- **产出**：75 篇版本快照标注现行版；日志折叠。
- **验收**：现行版明确可辨；旧版仍可检索到。
- **风险**：中。

## 6. 上下文安全（用户明确提出）

> "mimir系统未来变得庞大，会不会让agent上下文爆炸？"

**裁决：规模增长发生在存储侧，不进注入侧。** 三道既有闸必须接上，不得绕过：

| 闸 | 机制 | 位置 |
|---|---|---|
| 预算闸 | 超出 `limit` → `budget_exceeded` + 丢弃清单 | `query.py` |
| 深度闸 | 默认 `depth=standard` 只装配 L3+L2；L1 仅在 `deep` | `query.py:96` |
| 渐进披露 | 索引段/展开段三段式 | `recall_cursor.py` |

**新增约束**：`VaultIndexer` 的巡检结果（可能很大）**绝不直接进 agent 上下文**，
只落入 Mímir 内部；对 agent 暴露的永远是**带预算的窄接口**。

## 7. 已裁决事项（2026-10-28 用户确认）

### 7.1 库 = 共享目标（安全裁决，最高优先）

**实测事实**：库由 **Syncthing** 同步（`~/obsidian-vault/.stfolder` 存在），
且装有 `obsidian-git` 插件。git 本身无 remote（纯本地 commit）。

**裁决**：**目标库按 `target_scope='shared'` 处理。**

理由：内容会经 Syncthing 离开本机，物理上已属"共享"。因此：
- 复用 `_enforce_fact_policy`：`owner_only` 事实**不得**写入库；
  `restricted` 敏感度 + `local_only` 出站策略的事实**不得**写入库。
- `60-敏感信息/` 已在 `_FORBIDDEN_ROOTS`（existing），**不得**写入。
- 全部 `RegisterDocument` 默认 `target_scope='shared'`。

> **⚠️ 仅靠上面三条不够**：§7.7 实测证明真实密钥是以 `sensitivity=internal`
> + `visibility=all` 存着的，`_enforce_fact_policy` 的 `restricted` 判据
> **挡不住它们**。回流准入须按 §7.7 末段的**三重判据**执行，
> 不得只依赖敏感度标签。

### 7.2 自我摄入防护（防反哺成环）

**风险**：Mímir 写卡片入库 → `VaultCollector` 全量摄入 → 卡片正文被当作
新事实吃回 → 再结晶 → 循环。审查确认这是"会让反哺比现状更糟"的唯一失败模式。

**裁决**：Mímir 自己产出的卡片，**摄入侧按 frontmatter 标记排除**。
- 卡片首部写入机器可读标记（如 `mimir_generated: true` + `mimir_id`）。
- `VaultCollector` 增加过滤器：读到该标记 → 跳过正文摄入，
  仅登记"此卡片存在"（角色 `mimir-card`）。
- 该防护必须在**阶段 2 第一次写入之前**落地，并有测试专钉。

### 7.3 阶段 3 = 生成建议 diff，人工放行（不给自动改正文的权力）

**裁决**：采纳审查者方案 (b)。阶段 3 的机制是：
- `VaultIndexer` 产出**修复提案**（目标文件 + 当前行 + 建议改动 + 理由），
  落成可供人审的 diff 制品（committed JSON/MD，见 §7.5），
  **不直接改库**。
- 人工审阅批准后，由一次性补丁步骤应用。
- 后果：阶段 3 的"验收"依赖人工逐条参与；"死链归零"不是全自动指标，
  而是"提案生成完毕 + 人工放行后归零"。

### 7.4 本人自定的判断（非用户明示，标注以便核对）

| # | 判断 | 依据 |
|---|---|---|
| a | 回流卡片写入**新命名空间**（不改既有 PARA 目录），具体名待实现时定 | 混居是目标，但第一版不该既有结构里动土；先另开，验证后再谈并入 |
| b | 卡片正文**不含 volatile frontmatter 更新**（`last_verified`/`status` 机器不改），改为纯托管区块承载 | 见 §7.6 `human_content_hash` 缺陷：frontmatter 计入人类区，每次更新都会误报冲突 |
| c | 阶段 0 的安全网做成**独立脚本 + 可重跑清册制品**，不是一次性手工 commit | 638 篇的量化事实取自 n100 实扫，本机无法复现；清册须可重跑才可验收 |
| d | 首轮只回填**早报相关实体**（`model_card`/`tool_card`），不做全量实体回填 | 审查 #3：全量回填会灌满库，正好复现要修的乱；早报是已被验证的产出路径 |

### 7.5 可复现性要求

§1.3 的所有数字取自 n100 实扫，开发机无法复现。故阶段 1/3 的验收
必须基于**可重跑的清册制品**（committed JSON/MD），而非散文里的数字。

### 7.6 已知代码缺陷（实现前必须处理）

| 缺陷 | 位置 | 影响 |
|---|---|---|
| `_ALLOWED_ROOTS` 与真实库**对不上**：写 `00-系统`/`30-知识`/`90-机器收件箱`，真库是 `005-系统设计`/`30-知识库`/`90-自动同步_已归档_v3` | `publication.py:23` | 白名单照别的目录结构写的，**从未在真库验证**（因零调用）。必须改为**声明式配置**并纳入 `version_sweep` 同类扫描 |
| `human_content_hash` 把 **YAML frontmatter 也算作人类区** | `publication.py:625` | 每次 Mímir 更新 frontmatter 都触发冲突误报 → 见 §7.4-b 的规避 |
| `DOCUMENT_TYPES` 是封闭 5 值集，**无"实体卡片"类型** | `schema.py:77` | 卡片注册要么扩枚举（需 schema 迁移），要么走独立写入器。见下 |
| `PublicationService` 要求 `actor_principal == "service:vault_adapter"` | `schema.py:76` | 该 principal 须真实存在于 auth registry，否则调用即失败 |

**关于 `DOCUMENT_TYPES`**：本人判断（标注待核）——**卡片走扩枚举**，
新增 `entity_card` 类型，配 schema 迁移段。理由：让卡片与人类页面共用
同一套 `managed sections` 保护与审计链，胜过另造一个绕过保护的写入器。
代价：一次 schema 版本动作 + `version_sweep` 登记。

### 7.7 生产库实测（2026-10-28，批准前补查）

**生产库定位纠错**：`~/.hermes/mimir/data/canonical.db` 是 10-09 残留（**全表 0 条**，
查它会得出"没摄入过任何东西"的假阴性）。真生产库是
`~/.hermes/mimir/v9/production-v9.0-20260805_214614/canonical.db`
（服务 `mimir_v8.server` 自 10-09 跑在此路径），**1068 条事实 / 985 条来源记录**。

| 检查项 | 结果 |
|---|---|
| `60-敏感信息/` 是否被摄入 | **否**（`source_id` 匹配 0 条）→ 存量干净，只需管住未来 |
| 正文含 `sk-` 的事实 | **7 条**，其中真实密钥片段 3 条（`sk-4166fcd0…` ×2、`sk-sKLY…` ×1），另 4 条为占位/截断 |
| 这 7 条的出站策略 | 全部 `egress_policy=local_only`（未出本机） |
| 这 7 条的敏感度标签 | 6 条 `sensitivity=internal` + `visibility=all`；1 条 `owner_only` |

**由此得出的一条硬判据（补入 §7.1）**：回流的准入**不能只信 `sensitivity` 标签**。
实测证明密钥明文是以 `internal` 存着的——若准入只判 `sensitivity=='restricted'`，
这批内容会被判为"可发布"。故回流准入必须**同时**满足：
1. `egress_policy == 'local_only'` 或更强（本就如此），且
2. `visibility != 'all'`（`all` 意味着同库其他 agent 可读），且
3. **正文通过密钥/凭据形态扫描**（`sk-`、`AKIA`、私钥块、长 hex 等）方可在库内流转，
   命中者一律不得进入 `ObsidianPublisher` 的候选集。

> 注：本节实测到的 7 条存量是否需处置（改写/加标记），属"存量治理"，
> 不在 1.7.0 范围内，但应记入待办——因为它证明"标签不足以表达真实敏感度"。
