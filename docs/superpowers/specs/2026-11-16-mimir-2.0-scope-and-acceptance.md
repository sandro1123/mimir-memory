## 1. 问题：现在有三个互不相容的「2.0」

| 出处 | 2.0 是什么 | 与代码的关系 |
|---|---|---|
| README 第 209 行 | 统一 MCP/CLI 一键分发 + Command Center 大盘 + 开源正式发布 | 全是发布动作，没有一条可测的语义 |
| `2026-10-26` 规格 §8 | 上述三件 + 双池一桥「收官」 | 该文还写着第五投影器 `ObsidianProjector`、52 张表、`Personal/` 物理锁——**这三条代码里都不存在**，CHANGELOG 1.7.0 段已否认 |
| `2026-11-12` 路线图 | 双时态 `valid_time`/`transaction_time` + 统一脑 | 方向正确，但把 2.0 排在 1.9 之后、只争取一份预研设计稿 |

后果不是文档不整齐，而是**终点线不可证伪**：任何一版都可以自称「2.0 在路上」，
而 README 仍把已作废的 10-26 规格当作「完整 2.0 规格设计」链接出去，后来者会照它开发。

## 2. 裁决

**2.0.0 =「能问过去的记忆」+ 开源前的安全门 + 可分发性。四项 gate 全部由可执行命令判定。**

| Gate | 内容 | 判定者 |
|---|---|---|
| **G1 双时态语义** | `valid_time`（事实何时为真）+ `transaction_time`（系统何时得知）+ `as_of` 查询 | 金标回放 |
| **G2 谱系归一** | 一套结构化 supersession 真相，旧读路径降为兼容视图 | 测试 + grep |
| **G3 开源安全门** | 联邦按收件人隔离密钥 + 逐事件签名 + Vault 写入路径校验 | 三条反向注入钉 |
| **G4 可分发性** | 干净机器 pip / docker 60 秒可用；双语文档与代码一致 | 干净环境脚本 |

**明确不阻塞 2.0**：Command Center 大盘（→ 1.9.x 交付，若做）、Obsidian 双向同步、
遍历式图推理、情绪/意图推断、多租户 SaaS。

理由：前四件是"系统变得可以说它懂了什么"的结构性变化；后者是产品面，
放在 2.0 里只会把大版本变成无限期容器——这正是 10-26 规格犯的错。

| 版本 | 交付 | SCHEMA | 迁移段 |

**硬规则**：
1. 一个 minor 版本最多一次 schema bump。
2. bump 必须同一个 PR 内包含：迁移段 + `MIGRATABLE_TARGET_VERSIONS` 登记 +
   `test_p0o_version_domains` / `test_r8_release` 绿 + README schema 徽标 + CHANGELOG。
3. **不得给 `memory_events` / `fact_versions` 的历史行做 UPDATE 回填**——触发器会
   `RAISE(ABORT)`。历史行的 `transaction_time` 用 `occurred_at` 解释，新事件显式写入。

## 5. 验收判据（每条都可证伪）

**G1 双时态**
- `as_of` 金标回放：同一 24 条金标、同一装配面，`hit@5 ≥ 0.875`、`hit@10 ≥ 0.917`（与 `docs/RESULTS.md` 今日口径对齐），report 入 `docs/RESULTS.md`。
- `recall_verdict` 在 `as_of` 下必须区分三种状态：`found` / `not_yet_known`（当时系统还不知道）/ `never_existed`（从未存在）。**把「当时不知道」报成 `not_found` 视为未完成。**
- 迁移 23→24 在生产快照副本上跑通，`scripts/prod_drift.py` 报 `table_drift=NONE`。

**G2 谱系归一**
- `rg "relation_type=['\"]supersede" mimir_v8/` 零命中（写路径只剩 `fact_supersessions`）。
- `tests/test_p44_supersede.py`、`test_p30_temporal_graph.py` 全绿；旧 `relations` 读路径经视图仍返回历史形状。
- 反向注入：直接往旧 `relations` 写 supersede 边的路径已被封死（测试断言拒绝）。

**G3 开源安全门**（三条都以「反向注入必红」证明）
- 收件人隔离：节点 A 持有发给节点 B 的信封时解密必失败；A 的同级 peer C 同样必失败。
- 逐事件签名：篡改 `(crdt_key, lamport, node_id, op, value)` 任一字段 → ingest 拒收；未注册节点签名 → 拒收；无签名事件 → 拒收（fail-closed）。
- Vault 路径：卡片目标路径存在符号链接、或解析后落在 `vault_root` 之外 → 拒绝写入且不留残留文件。

**G4 可分发性**
- 干净容器：`pip install mimir-v8 && mimir-server` 60 秒内 `GET /health` 返回 `status:ok` 且 `schema_version` 与 `SCHEMA_VERSION` 一致。
- `docker compose up` 同判据。
- `python scripts/version_sweep.py`、`python scripts/release_scan.py`、`ruff check mimir_v8/` 全绿；README 与 README_en 的版本/表数/能力表述一致。

## 6. 从 1.x 继承、2.0 不得破坏的承诺

1. `UPDATE`/`DELETE` **永不自动**（自动获取 ≠ 自动入库）。
2. 一切新记忆先过候选队列与三档判重。
3. 预算诚实：超限显式返回 `budget_exceeded` 与丢弃清单，不换虚假 stub。
4. **忘 ≠ 删**：衰减只归档，删除必须先进账本。
5. 无 LLM 时只走 Tier-0 确定性路径，不降级为"全文暂存"。
6. 每次机器写入 Vault 前后各一次 Git 快照；人类手写区永不被覆盖。
7. 每次外部召回都带 `recall_verdict`，降级不得冒充成功。

---

## 7. 反目标（2.0 期间坚决不做）

- 不做全自动直接写库（绕过候选评审）。
- 不做"搜得多就算热"（回声闭环是首要 anti-pattern）。
- 不引入 JSON 文件锁、外部向量库或第二个真相源。
- 不重写 `dashboard/backend/main.py` 的 `/api/*` 契约（前端换壳不得逼后端改面）。
- 不为"显得完整"增加情绪识别、意图推断、跨用户画像合并。
- 不在安全门（G3）之前对外发布仓库或打 2.0 tag。
